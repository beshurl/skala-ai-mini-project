# 기능별 실행 결과와 발표 시연 안내

**SKALA 광주 2반 · G066 · 정준용**

가설 비교와 Judge·추적 결과는 **2026년 10월 21일 보존된 실제 Ollama 실행**, 보고서 검증 화면은 **10월 22일 실제 재실행**의 발췌다. 지표·로그·추가 관측은 교육용 합성 데이터이며 이번 발표 수정에서 LLM 평가를 재실행하지 않았다. 계획·작성 모델은 qwen3.5:2b, 별도 Judge는 qwen3:8b다.

[발표 PPT](운영진단_에이전트_5분발표.pptx?raw=true), [5분 대본·연결 멘트](../PRESENTATION_5MIN.md), [실행 결과 발췌 JSON](assets/execution-evidence.json)을 함께 확인한다.

## 1. 가설별 원인 구별: 6페이지

**실제 입력 질문**

> payments-service CPU가 91%이고 중복 배치 경고가 있습니다. 실제 원인을 다른 가설과 구별해주세요.

두 실행은 모두 개선 버전이며 최초 CPU 91%와 배치 경고를 같게 두고 추가 관측 조건을 달리했다. 버전 전후 성능 측정과 구분한다.

| 확인 내용 | batch 실행 | traffic 실행 |
| --- | --- | --- |
| 배치 CPU 기여 | 86% | 5% |
| 추가 관측 | 중복 활성 작업 2개·중첩 4분 | 요청 처리 기여 88%·요청량 100→320 RPS |
| 실제 답변 발췌 | 중복 배치 작업의 CPU 점유 (교차 지지) | 요청량 증가에 따른 CPU 점유 (교차 지지) |
| 실제 추가 조회 | 3회 | 2회 |

발표에서는 같은 첫 경고에서도 최종 판단이 달라진 점을 짚는다. 교차 지지는 실제 인과관계 확정과 구분한다.

## 2. 추가 조사 과정: 4~5페이지

traffic 실행의 실제 순서는 다음과 같다.

1. CPU 점유가 실제 어느 작업에 귀속되는지 확인한다.
2. 평소 대비 요청량과 지속 시간을 확인한다.
3. 한 가설의 두 종류 관측이 교차 지지하고 경쟁 가설이 반증되어 조사를 종료한다.

[실제 조사 화면](../../artifacts/screenshots/investigation-traffic-desktop.png)에서 관측·판단 전후·조사 이유를 보여준다. 6페이지와 같은 수치를 반복하지 않고 조회 순서와 종료 이유를 설명한다.

## 부분 실패 대응: 7페이지

[가설 조사 평가 원본](../../artifacts/investigation_evaluation.json)의 `probe-failure`는 CPU 귀속 도구의 타임아웃을 주입한 실제 LLM 사례다. `partial_retained=true`, `expected_conclusion=true`, `outcome=판단 보류`를 확인했다. 성공 관측을 보존하되 원인 확정에 필요한 근거가 없다는 한계를 표시했다. 일시 오류 재시도 구현과 타임아웃 주입 결과를 동일한 검증으로 혼동하지 않는다.

## 3. RAG와 근거 검증: 8~9페이지

2026-10-22 실제 Ollama로 같은 batch 질문을 다시 실행했다. [원본 프론트 화면](assets/live-validation-20261022.png)과 [같은 실행의 검증 로그](assets/live-validation-20261022.json)를 보존했다. 9페이지에는 최종 보고서 검증 영역을 확대해 시스템명·수치·상태·알림·근거 ID·조치 조건·필수 항목과 작성 2회·재작성 1회를 보여준다.

이 실행에서도 CPU 급증 대응 절차, 메모리 누수 대응 절차, 응답 지연 대응 절차가 검색 후보로 수집됐다. CPU 급증 대응 절차의 검색 유사도는 0.696이며 확률이나 원인 확신도를 뜻하지 않는다. 검색 후보 전체를 조치에 적용하지 않고 관측 조건과 맞는 근거를 사용했다.

**실제 검증 이벤트 원문**

```json
[
  {
    "type": "Validation",
    "attempt": 1,
    "verdict": "불합격",
    "errors": [
      "action_ids: 확인 가능한 가설/다음 행동이 누락되었습니다."
    ]
  },
  {
    "type": "Validation",
    "attempt": 2,
    "verdict": "합격",
    "errors": []
  }
]
```

10월 21일 보존 실행에서는 첫 작성의 `action_ids`가 비어 있었고 두 번째 작성에는 `A:cpu-spike`가 포함됐다. 10월 22일 재실행도 다음 행동 누락으로 1차 검사에서 불합격하고 2차 검사에서 통과했다. 저장된 최종 검증은 작성 2회·재작성 1회·통과다. 검사 항목은 시스템명, 수치, 상태·알림, 근거 ID, 조치 조건, 필수 항목이다. 수치 오류가 발생한 사례로 바꾸어 설명하지 않는다.

## 4. Judge와 LangSmith: 10~11페이지

| 실제 사례 | 기능 검사 | Judge 결과 | 종합 결과 |
| --- | --- | --- | --- |
| traffic | 통과 | 5개 항목 모두 5/5 | 통과 |
| release | 통과 | 근거 충실성 2/5, 나머지 항목 5/5 | 미통과 기록 보존 |

release는 Judge의 오판 검토 사례다. 전체 답변 원점수는 5/5였지만 별도 주장 대조가 지지·반증 조건을 혼동해 모순으로 판정했고, 상한 정책으로 최종 근거 점수는 2/5가 됐다. 원점수와 주장 대조, 최종 미통과를 모두 보존했다. 전체 6개 사례의 기능 검사는 6/6, Judge 포함 종합은 5/6이며 LangSmith 원격 실행 6건과 평가 점수 30개를 저장 후 재조회했다.

별도 입력 검사 도입 후 검증에서는 거절 5건의 생성 토큰과 LLM·MCP 호출이 0이었다. 자동 테스트 99개 통과 기록도 입력 검사 검증 원본에 보존했다.
