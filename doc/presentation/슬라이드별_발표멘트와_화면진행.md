## 2. 기존 문제와 개선 방향 (40초)

**대응 항목:** 2) 문제 개선 및 신규 구현 사항

**발표 멘트**

> 해결 과제는 네 가지였습니다. 먼저 업무와 무관한 입력까지 모델을 호출해 토큰과 시간이 들었습니다. 그래서 모델 실행 전에 입력을 검사했습니다. 다음으로 CPU 상승과 배치 경고만으로 원인을 추정하면 잘못된 조치를 권할 수 있어, 경쟁 가설과 추가 관측을 도입했습니다. 키워드 검색과 일부 조회 실패에는 다중 문서 검색과 실패 격리를 적용했습니다. 마지막으로 잘못된 수치와 반복 생성을 막기 위해 사실 검증과 호출 횟수 제한을 함께 설계했습니다.

**화면에서 짚을 부분**

표의 각 행에서 기존 문제와 개선 이유를 연결한다. 개선 기능만 나열하지 않고 왜 필요한지 설명한다.

## 3. 핵심 기능과 가설 조사 차별점 (40초)

**대응 항목:** 2) 문제 개선 및 신규 구현 사항

**발표 멘트**

> 가장 큰 차별점은 추가 조회 전에 지지와 반증 조건을 정한다는 점입니다. 실제 LLM이 아직 수행하지 않은 허용 질문을 고르고, 동일한 시간 구간의 관측을 조건과 대조합니다. 그 결과 단서 지지, 교차 지지, 반증, 상충, 판단 보류를 구분합니다. 전체 추가 조회는 최대 네 번입니다. 사용자 화면에서는 조사 이유와 조건, 판단이 달라진 과정을 볼 수 있습니다. 대상 확인과 후속 질문, 기록 복원, 배포 전후 수치 비교도 함께 제공합니다.

**화면에서 짚을 부분**

상단의 조건 기록·질문 선택·관측·가설 갱신 순서를 짚는다. 하단에서 화면과 기록 기능을 짧게 소개한다.

## 4. 전체 아키텍처와 처리 흐름 (40초)

**대응 항목:** 3) 적용 기술 요소 / 4) 구현 결과

**발표 멘트**

> 전체 흐름은 입력 검사에서 시작합니다. 통과한 질문은 LangGraph Supervisor가 대상 확인과 전문 조회를 조정합니다. 지표와 로그는 병렬로 수집하고, 실제 관측을 포함한 질의로 런북을 검색합니다. CPU 추가 조사 대상이면 계획과 관측, 판정을 반복하고, 그 외 진단과 배포 점검은 공통 보고 흐름으로 합류합니다. 사실 검증을 통과한 결과를 화면과 SQLite에 남깁니다. 조회 실패는 항목별로 격리하고, 별도 평가 경로에서 Judge와 LangSmith를 연결합니다.

**화면에서 짚을 부분**

흐름도를 왼쪽 위부터 오른쪽으로 읽고 아래쪽 조사·검증·결과 경로로 이어간다. 거절 분기와 별도 평가 경로를 구분한다.

## 5. 적용 기술과 역할 분리 (45초)

**대응 항목:** 3) 적용 기술 요소

**발표 멘트**

> 기술은 각 역할에 맞춰 적용했습니다. Multi-Agent는 지표, 로그, 런북 전문 서브그래프로 나누고 Supervisor가 조정합니다. 모든 전문 조회가 개별 LLM을 사용하는 구조는 아닙니다. MCP는 조회 Tool, 런북 원문 Resource, 공통 절차 Prompt를 제공합니다. RAG는 매뉴얼 여섯 종을 임베딩해 SQLite에 저장하고 코사인 유사도로 최대 세 개를 검색합니다. 소규모 문서에 맞춘 자체 벡터 인덱스입니다. 외부 연결은 의존성 주입으로 분리하고, FastAPI와 SSE, Vue, SQLite로 진행 표시와 기록 복원을 구현했습니다.

**화면에서 짚을 부분**

기술명보다 실제 적용 역할을 설명한다. 외부 Vector DB 제품이나 자율적인 전문 LLM 에이전트를 사용했다고 확대하지 않는다.

## 6. 검증과 관측 가능성 (35초)

**대응 항목:** 3) 적용 기술 요소

**발표 멘트**

> 검증은 세 층으로 나눴습니다. 첫째, 자동 테스트와 관측 계약으로 입력, 분기, 수치 범위를 확인합니다. 둘째, 답변의 대상과 수치, 출처, 허용 조치를 검사하고 최대 세 번 작성한 뒤에도 실패하면 확인된 관측만 제공합니다. 셋째, 별도 Judge가 근거 충실성과 수치, 조치 조건, 요청 충족, 다음 행동을 평가합니다. LangSmith에는 실행과 토큰, 점수를 기록한 뒤 원격으로 다시 조회합니다. Judge도 틀릴 수 있어 원래 점수와 실패를 보존했습니다.

**화면에서 짚을 부분**

자동 검사, 답변 검증, 별도 의미 평가의 역할을 차례로 설명한다. Judge는 매 대화의 최종 승인기가 아니라 별도 평가임을 밝힌다.

## 7. 실행 화면과 실제 검증 결과 (45초)

**대응 항목:** 4) 구현 결과

**발표 멘트**

> 왼쪽은 실제 모델로 실행해 저장한 화면입니다. CPU 91%와 배치 경고가 있어도, 배치의 CPU 기여가 5%라 배치 가설은 반증했습니다. 요청 처리 기여 88%와 요청량 3.2배는 요청량 가설을 교차 지지했습니다. 관측 자체는 교육용 합성 데이터입니다. 오른쪽은 10월 21일 검증 기록입니다. 입력 거절 다섯 건은 생성 0토큰과 LLM, MCP 호출 부재를 확인했습니다. 자동 테스트는 99개를 통과했습니다. 입력 검사 도입 전 가설 평가는 기능 6건을 통과했고 Judge 포함 종합은 5건 통과였습니다. 원격 실행 6건과 점수 30개도 재조회했습니다.

**화면에서 짚을 부분**

저장 화면에서 배치 반증과 요청량 교차 지지를 보여준다. 표에서 입력 거절 검증과 그 도입 전 모델 평가를 구분한다. 실시간 전체 조사나 Judge는 재실행하지 않는다.

## 8. 한계와 다음 개선, 배운 점 (35초)

**대응 항목:** 5) 교훈

**발표 멘트**

> 입력 규칙은 토큰을 쓰지 않지만 오탐과 미탐이 생길 수 있습니다. 추가 조사도 CPU 세 가설과 합성 관측에 한정되며, 두 근거의 지지가 인과관계 확정을 의미하지 않습니다. Judge 역시 평가 오류가 있었습니다. 다음에는 실제 모니터링과 다른 계열 Judge, 사람 평가를 연결하고 동일 조건의 비용을 측정하겠습니다. 이번 경험을 통해 자연스러운 설명보다 판단 조건과 근거를 남기는 일이 중요하다는 점을 배웠습니다. 결론을 보류할 때도 이유를 설명하는 서비스로 설계했습니다.

**화면에서 짚을 부분**

한계와 그에 대응하는 향후 개선을 연결한다. 마지막 소감 한 문장을 읽고 5분 안에 종료한다.

## 시연 순서와 시간 관리

발표는 PPT 안에서 진행한다. 슬라이드 7의 저장 화면으로 배치 반증과 요청량 교차 지지를 설명하고, 전체 조사나 Judge 재평가를 발표 중 재실행하지 않는다.

짧은 시연이 필요한 경우 슬라이드 7의 설명 시간 안에서 시스템을 선택한 뒤 `오늘 날씨 알려줘`를 입력한다. 거절 이유와 생성 0토큰만 확인하고 PPT로 돌아온다. 서버가 준비되지 않았다면 [저장된 입력 거절 화면](../../artifacts/screenshots/input-rejected-zero-tokens.png)을 사용한다.

추가 조사 화면을 별도로 보여줄 때는 다음 순서로 진행한다.

1. `중복 배치 경고, 정말 원인일까요?` 예시와 `배치 단서 반증 · 요청량 증가` 샘플을 선택한다.
2. 조사 이유와 조회 전 판정 조건을 확인한다.
3. 배치 CPU 기여 5%의 반증, 요청 처리 기여 88%와 요청량 3.2배의 교차 지지를 짚는다.
4. 관측은 합성 데이터이고 인과 확정은 아니라는 범위를 설명한다.

## 예상 질문과 답변

**Q. 기존 RAG나 추가 조회와 무엇이 다른가요?**

조회 전에 지지·반증 조건을 기록하고, 경쟁 가설을 구별할 질문을 선택합니다. 최종 답변뿐 아니라 판단이 달라진 이유와 종료 이유도 관측 근거로 남깁니다.

**Q. 실제 AI를 연결했나요? 실제 운영 데이터인가요?**

보존된 실측은 Ollama의 qwen3.5:2b로 계획·작성하고 qwen3:8b로 별도 평가했습니다. 지표·로그·추가 관측은 교육용 합성 데이터입니다. OpenAI 연결도 지원하지만 해당 저장 결과에는 사용하지 않았습니다.

**Q. Multi-Agent는 모든 역할이 각각 LLM인가요?**

지표·로그·런북 역할을 전문 서브그래프로 분리하고 Supervisor가 조정합니다. 전문 조회는 도구와 검색을 담당하며, 실제 LLM은 추가 질문 선택과 보고서 후보 작성에 사용합니다.

**Q. Vector DB는 무엇을 사용했나요?**

매뉴얼 6종에 맞춰 임베딩을 SQLite에 저장하고 NumPy 코사인 유사도로 검색하는 자체 영속 벡터 인덱스를 구현했습니다. Chroma나 FAISS 같은 외부 제품은 사용하지 않았습니다.

**Q. 0토큰이면 전체 비용을 줄였다는 뜻인가요?**

거절한 5건의 생성 토큰이 0이고 LLM·MCP 호출이 없음을 검증한 결과입니다. 전체 요청 대비 절감률과 하드웨어 비용까지 측정한 것은 아닙니다.

**Q. 기능 6/6인데 종합 평가는 왜 5/6인가요?**

릴리스 사례는 기능 조건을 충족했지만 Judge가 근거 점수를 낮게 준 검토 사례입니다. 기능과 의미 평가를 구분하고 원래 실패 점수를 보존했습니다. Judge 역시 오류 가능성이 있습니다.

**Q. 두 근거가 지지하면 원인을 확정할 수 있나요?**

현재 정책에서 교차 지지로 표시할 수 있지만 실제 인과관계 확정은 별도의 운영 검증이 필요합니다. 관측이 상충하거나 부족하면 판단을 보류합니다.

**Q. 왜 추가 조사를 최대 4회로 제한했나요?**

허용한 관측 종류가 네 가지이고 중복을 막아 호출량을 통제하기 위해서입니다. 한도 때문에 미확인 가설이 남을 수 있으며 최소 호출 경로를 수학적으로 보장하지는 않습니다.

**Q. 다음에 가장 먼저 개선할 부분은 무엇인가요?**

실제 모니터링과 프로파일러 연결, 입력 필터의 사람 라벨 평가, 다른 계열 Judge와 사람 평가의 비교입니다. 동일 조건의 호출량·토큰·지연시간도 계측하겠습니다.

## 검증 결과의 출처와 해석 범위

모든 수치는 2026년 10월 21일 보존 기록이다. 이번 발표 구성 변경 과정에서는 실제 모델 평가를 재실행하지 않았다.

- [입력 validation 원본](../../artifacts/input_validation_verification.json): 입력 거절 5건 생성 0토큰, LLM·MCP 0회, 테스트 99개 통과.
- [가설 조사 평가 원본](../../artifacts/investigation_evaluation.json): 입력 검사 도입 전 실제 모델 평가. 기능 6/6, Judge 포함 종합 5/6, 원격 실행 6건·평가 점수 30개 재조회.
- [실제 추가 조사 저장 화면](../../artifacts/screenshots/investigation-traffic-desktop.png): 합성 관측에서 배치 반증과 요청량 교차 지지.

Judge는 별도 품질 평가이며 매 대화의 최종 승인기로 설명하지 않는다. SQLite는 완료 결과와 후속 맥락을 복원하며 실행 중 그래프 체크포인트 재개는 지원하지 않는다.
