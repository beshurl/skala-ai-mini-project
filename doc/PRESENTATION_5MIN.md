## 3. 질문과 실제 진단 답변 (45초)

**발표 멘트**

**슬라이드를 넘기면서**

## 4. 가설 조사 절차와 실행 기록 (55초)

**발표 멘트**

> 먼저 관측을 읽기 전에 가설별 지지·반증 기준을 고정합니다. LLM이 미수행 질문을 고르고 MCP가 관측을 가져오면 코드가 조건과 대조합니다. 오른쪽은 실제 요청량 사례의 조사 화면입니다. 첫 조사에서 CPU가 어느 작업에 귀속되는지 확인하고, 다음 조사에서 평소 대비 요청량과 지속 시간을 확인했습니다. 서로 다른 관측이 교차 지지하고 경쟁 가설이 반증돼 두 번 만에 종료했습니다. 화면에는 조사 이유와 판단 전후도 남깁니다. 근거가 부족하면 최대 네 번 조사하고, 끝까지 부족하거나 상충하면 보류합니다. 보고서는 이어서 별도 근거 검증을 거칩니다.

**슬라이드를 넘기면서**

> 전체 서비스에서는 이 흐름을 다음과 같이 연결했습니다.

**화면에서 짚을 부분**

왼쪽 절차와 오른쪽 실제 조사 화면을 연결한다. 하단의 1차·2차 조회와 종료 이유를 짚고 사례 수치는 다시 읽지 않는다.

## 5. 전체 아키텍처 (45초)

**발표 멘트**

> Vue 화면에서 질문을 보내면 FastAPI가 요청과 대상을 확인합니다. LangGraph가 전문 조회와 추가 조사, 보고서 작성을 조정합니다. LLM은 질문 선택과 작성에 사용하고, MCP는 관측 조회, RAG는 매뉴얼 검색을 담당합니다. 진행 상황은 SSE로 전달하고 완료 결과와 대화 맥락은 SQLite에 저장합니다. 평가와 추적은 별도 경로로 연결했습니다.

**슬라이드를 넘기면서**

> 이 중 근거 검증이 실제로 동작한 사례를 보겠습니다.

**화면에서 짚을 부분**

전체 아키텍처 한 장에서 Vue, FastAPI, LangGraph 경로와 연결된 도구·모델·기록·평가 역할을 짚는다.

## 6. 적용 기술과 재작성 실행 결과 (45초)

**발표 멘트**

> 왼쪽은 기술별 역할이고, 오른쪽은 실제 배치 사례의 작성 기록입니다. RAG는 CPU 급증 대응 절차 등 관련 런북 세 종을 검색했습니다. 첫 초안은 확인 가능한 다음 행동이 빠져 코드 검사에서 불합격했습니다. 피드백을 반영한 두 번째 작성에서는 허용된 조치가 포함돼 통과했습니다. 즉, 이 사례는 재작성 한 번이 실제로 발생한 기록입니다. 대상과 수치, 근거 ID와 조치 조건을 코드가 검사하고, Judge는 별도 품질 평가를 담당합니다.

**슬라이드를 넘기면서**

> 그 별도 평가와 원격 추적 결과도 확인했습니다.

**화면에서 짚을 부분**

왼쪽 RAG 검색 결과와 오른쪽 실제 1차 불합격·2차 합격 이벤트를 짚는다. 재작성 1회가 발생한 보존 실행임을 설명한다.

## 7. 실제 LLM 평가·추적 결과 (40초)

**발표 멘트**

> 자동 테스트는 99개를 통과했습니다. 입력 검사 도입 전 실제 Ollama의 가설 조사 여섯 건은 기능 검사 모두 통과했고, Judge 포함 종합은 다섯 건 통과였습니다. 아래 개별 결과에서 요청량 사례는 다섯 평가 항목 모두 5점이었지만, 릴리스 사례는 Judge 근거 점수가 2점이어서 종합 미통과로 남았습니다. LangSmith 실행 여섯 건과 점수 서른 개도 재조회했습니다. 입력 검사 도입 후 거절 다섯 건은 생성 0토큰이었습니다.

**슬라이드를 넘기면서**

> 마지막으로 이 결과의 한계와 다음 과제입니다.

**화면에서 짚을 부분**

상단 전체 수치와 하단 traffic·release 개별 점수를 연결한다. 원격 추적 재조회 결과와 별도 입력 거절 검증을 짧게 언급한다.

## 8. 한계와 다음 개선, 배운 점 (30초)

**발표 멘트**

**화면에서 짚을 부분**

## 시연과 시간 관리

3번에서 질문과 실제 답변을 비교하고, 4번에서 조회 순서와 종료 이유를 짚는다. 6번은 기술 표를 전부 읽기보다 실제 불합격·재작성·통과 기록을 중심으로 설명한다. 7번은 전체 통과 수치와 개별 평가 결과를 연결한다.

입력 validation은 2번 보조 기능과 7번 각주에서 짧게 언급한다. 전체 조사와 Judge 재평가는 발표 전에 완료한 보존 결과로 설명하며 현장에서 장시간 LLM 호출을 기다리지 않는다.

## 예상 질문과 답변

**Q. 기존 RAG나 추가 조회와 무엇이 다른가요?**

조회 전에 지지·반증 조건을 기록하고, 경쟁 가설을 구별할 질문을 선택합니다. 최종 답변뿐 아니라 판단이 달라진 이유와 종료 이유도 관측 근거로 남깁니다.

**Q. 실제 AI를 연결했나요? 실제 운영 데이터인가요?**

보존된 실측은 Ollama의 qwen3.5:2b로 계획·작성하고 qwen3:8b로 별도 평가했습니다. 지표·로그·추가 관측은 교육용 합성 데이터입니다. OpenAI 연결도 지원하지만 해당 저장 결과에는 사용하지 않았습니다.

**Q. Multi-Agent는 모든 역할이 각각 LLM인가요?**

지표·로그·런북 역할을 전문 서브그래프로 분리하고 Supervisor가 조정합니다. 전문 조회는 도구와 검색을 담당하며, 실제 LLM은 추가 질문 선택과 보고서 후보 작성에 사용합니다.

**Q. Vector DB는 무엇을 사용했나요?**

매뉴얼 6종에 맞춰 임베딩을 SQLite에 저장하고 NumPy 코사인 유사도로 검색하는 자체 영속 벡터 인덱스를 구현했습니다. Chroma나 FAISS 같은 외부 제품은 사용하지 않았습니다.

**Q. 0토큰이면 전체 비용을 줄였다는 뜻인가요?**

거절한 5건의 생성 토큰이 0이고 LLM·MCP 호출이 없음을 검증한 결과입니다. 전체 요청 대비 절감률과 하드웨어 비용까지 측정한 것은 아닙니다.

**Q. 기능 6/6인데 종합 평가는 왜 5/6인가요?**

릴리스 사례는 기능 조건을 충족했지만 Judge가 근거 점수를 낮게 준 검토 사례입니다. 기능과 의미 평가를 구분하고 원래 실패 점수를 보존했습니다. Judge 역시 오류 가능성이 있습니다.

**Q. 두 근거가 지지하면 원인을 확정할 수 있나요?**

현재 정책에서 교차 지지로 표시할 수 있지만 실제 인과관계 확정은 별도의 운영 검증이 필요합니다. 관측이 상충하거나 부족하면 판단을 보류합니다.

**Q. 왜 추가 조사를 최대 4회로 제한했나요?**

허용한 관측 종류가 네 가지이고 중복을 막아 호출량을 통제하기 위해서입니다. 한도 때문에 미확인 가설이 남을 수 있으며 최소 호출 경로를 수학적으로 보장하지는 않습니다.

**Q. 다음에 가장 먼저 개선할 부분은 무엇인가요?**

실제 모니터링과 프로파일러 연결, 입력 필터의 사람 라벨 평가, 다른 계열 Judge와 사람 평가의 비교입니다. 동일 조건의 호출량·토큰·지연시간도 계측하겠습니다.
