## 2. 핵심 개선: 추가 조사와 근거 검증 (30초)

**슬라이드를 넘기면서**

**슬라이드를 넘기면서**

## 4. 가설 조사 절차와 실행 기록 (60초)

**발표 멘트**

> 가장 중요한 설계는 관측을 조회하기 전에 판정 조건을 정한다는 점입니다. 예를 들어 특정 작업의 CPU 기여 비중이 70% 이상이면 해당 가설을 지지하도록 기준을 먼저 고정합니다. 이후 LLM은 남은 조사 후보 중 필요한 질문을 선택합니다. MCP가 관측을 가져오면, 코드가 미리 정한 조건과 대조해 가설 상태를 갱신합니다. 질문 선택과 수치 판정의 책임을 나눈 것입니다. 오른쪽 사례에서는 CPU가 어느 작업에 사용됐는지 확인한 뒤 요청량과 지속 시간을 조사했습니다. 서로 다른 관측이 같은 가설을 지지하고 경쟁 가설의 반증도 확보돼 종료했습니다. 화면에는 조사 이유, 판정 조건, 관측 결과를 남깁니다. 추가 조회는 최대 네 번이며, 근거가 부족하거나 상충하면 원인 확정을 보류합니다.

**슬라이드를 넘기면서**

> 이 흐름을 전체 시스템에서는 다음과 같이 연결했습니다.

**화면에서 짚을 부분**

왼쪽 사전 조건의 CPU 기여 70% 예시를 짚고 LLM 질문 선택·코드 판정·종료 역할을 구분한다. 오른쪽 실제 조회 순서와 종료 이유를 연결한다.

## 5. 전체 아키텍처 (55초)

**발표 멘트**

> Vue에서 질문을 보내면 FastAPI가 입력과 조사 대상을 확인합니다. 중앙의 LangGraph는 Supervisor 역할로 전문 조회와 추가 조사, 보고서 작성을 조정합니다. 지표와 로그는 병렬로 수집하고, 런북은 수집한 관측을 반영해 검색합니다. 전문 역할을 서브그래프로 분리해 일부 조회가 실패해도 성공한 근거는 유지하도록 했습니다. MCP에서는 Tool로 관측을 조회하고, Resource로 런북 원문을 제공하며, Prompt로 공통 조사 절차를 전달합니다. 진행 상황은 SSE로 화면에 전달하고 완료 결과와 대화 맥락은 SQLite에 저장합니다. 모델과 도구 연결은 의존성 주입으로 분리해 테스트할 때 교체할 수 있도록 했습니다.

**슬라이드를 넘기면서**

> 다음은 검색한 근거가 실제 보고서 검증으로 이어진 화면입니다.

**화면에서 짚을 부분**

Vue에서 FastAPI와 LangGraph로 이동하며 전체 구조를 짚는다. 전문 조회 병렬 수집과 관측 기반 검색, MCP·저장·평가 연결을 설명한다.

## 6. 적용 기술과 실제 검증 화면 (50초)

**발표 멘트**

> RAG는 매뉴얼 여섯 종을 임베딩해 의미가 가까운 문서를 검색합니다. 벡터는 SQLite에 저장하고 NumPy로 유사도를 계산했습니다. 현재 문서 규모에 맞춰 별도 검색 서버 없이 구성했습니다. 검색 결과는 MCP의 원문과 대조하고, 관측 조건에 맞는 문서를 보고서 근거로 사용합니다. 오른쪽은 실제 Ollama로 재실행한 화면입니다. 첫 초안은 확인 가능한 다음 행동이 빠져 코드 검사에서 불합격했습니다. 피드백을 반영한 두 번째 작성은 통과했습니다. 화면에서도 여섯 검증 항목과 작성 두 회, 재작성 한 회를 확인할 수 있습니다.

**슬라이드를 넘기면서**

> 코드 검사 외에, 답변의 품질과 실행 기록도 별도로 평가했습니다.

**화면에서 짚을 부분**

왼쪽 MCP 인터페이스 역할과 RAG 벡터 저장·검색 구성을 짚고 오른쪽 실제 프론트의 검증 완료·작성 2회·재작성 1회를 확인한다. 화면은 최종 상태이며 1차 누락 사유는 저장된 이벤트 근거다.

## 7. 실제 LLM 평가·추적 결과 (45초)

**발표 멘트**

> 보존된 검증 결과에서 코드 분기와 오류 처리를 검사하는 자동 테스트 99개가 통과했습니다. 실제 LLM을 사용한 가설 조사 여섯 사례도 기능 검사를 모두 통과했습니다. 별도 Judge는 근거 충실성, 수치 정확성, 조치 조건 등을 평가했습니다. 릴리스 사례는 기능 검사를 통과했지만 Judge 점수가 낮아 종합 결과는 여섯 건 중 다섯 건이었습니다. 이 차이를 숨기지 않고 검토 대상으로 남겼습니다. LangSmith에서는 실행 여섯 건과 평가 점수 서른 개를 재조회해 원격 저장까지 확인했습니다. 별도로 입력 거절 다섯 건에서는 생성 토큰이 0임을 검증했습니다.

**슬라이드를 넘기면서**

99개 자동 테스트와 실제 모델의 6/6 기능 검사·5/6 종합을 구분한다. LangSmith의 실행·평가 점수 재조회와 별도 생성 0토큰 결과를 짧게 설명한다.

## 8. 한계와 다음 개선, 배운 점 (30초)

**발표 멘트**

> 현재는 CPU 관련 세 가설과 합성 관측에 한정됩니다. 조회 한도는 비용을 통제하지만 미확인 가설을 남길 수 있고, Judge에도 오판 가능성이 있습니다. 앞으로 실제 모니터링을 연결하고, 다른 계열 모델과 사람 평가를 비교하며 전체 비용을 계측하겠습니다. 이번 프로젝트를 통해 판단 조건과 근거를 함께 남겨야, 진단이 달라진 이유까지 설명할 수 있다는 점을 배웠습니다. 감사합니다.

**화면에서 짚을 부분**

CPU 범위와 조회 한도에 따른 미확인 항목, Judge 오류를 다음 개선과 연결하고 판단 조건·근거 기록의 교훈으로 마무리한다.

## 시연과 시간 관리

3번은 결과가 달라진 이유, 4번은 사전 판정 조건과 조사 선택, 5번은 각 기술의 책임, 6번은 프론트 검증 완료 상태와 작성·재작성 횟수, 7번은 기능 검사와 Judge 평가의 차이에 집중한다. 같은 수치를 여러 장에서 반복해 읽지 않는다.

입력 검사는 보조 기능으로 짧게 설명한다. 발표 중 전체 LLM 조사나 Judge 재평가를 기다리지 않고 보존한 실제 실행 화면을 사용한다. 목표 시간은 5분 30초이며 발표 속도와 화면을 짚는 시간에 따라 조금 달라질 수 있다.

## 예상 질문과 답변

**Q. 기존 RAG나 추가 조회와 무엇이 다른가요?**

조회 전에 지지·반증 조건을 기록하고, 경쟁 가설을 구별할 질문을 선택합니다. 최종 답변뿐 아니라 판단이 달라진 이유와 종료 이유도 관측 근거로 남깁니다.

**Q. 실제 AI를 연결했나요? 실제 운영 데이터인가요?**

보존된 실측은 Ollama의 qwen3.5:2b로 계획·작성하고 qwen3:8b로 별도 평가했습니다. 지표·로그·추가 관측은 교육용 합성 데이터입니다. OpenAI 연결도 지원하지만 해당 저장 결과에는 사용하지 않았습니다.

**Q. Multi-Agent는 모든 역할이 각각 LLM인가요?**

지표·로그·런북 역할을 전문 서브그래프로 분리하고 Supervisor가 조정합니다. 전문 조회는 도구와 검색을 담당하며, 실제 LLM은 추가 질문 선택과 보고서 후보 작성에 사용합니다.

**Q. Vector DB는 무엇을 사용했나요?**

매뉴얼 6종에 맞춰 임베딩을 SQLite에 저장하고 NumPy 코사인 유사도로 검색하는 자체 영속 벡터 인덱스를 구현했습니다. Chroma나 FAISS 같은 외부 제품은 사용하지 않았습니다.

**Q. 0토큰이면 전체 비용을 줄였다는 뜻인가요?**

거절한 5건의 생성 토큰이 0이고 LLM·MCP 호출이 없음을 검증한 결과입니다. 전체 요청 대비 절감률과 하드웨어 비용까지 측정한 것은 아닙니다.

**Q. 기능 6/6인데 종합 평가는 왜 5/6인가요?**

릴리스 사례는 기능 조건을 충족했지만 Judge가 근거 점수를 낮게 준 검토 사례입니다. 기능과 의미 평가를 구분하고 원래 실패 점수를 보존했습니다. Judge 역시 오류 가능성이 있습니다.

**Q. 두 근거가 지지하면 원인을 확정할 수 있나요?**

현재 정책에서 교차 지지로 표시할 수 있지만 실제 인과관계 확정은 별도의 운영 검증이 필요합니다. 관측이 상충하거나 부족하면 판단을 보류합니다.

**Q. 왜 추가 조사를 최대 4회로 제한했나요?**

허용한 관측 종류가 네 가지이고 중복을 막아 호출량을 통제하기 위해서입니다. 한도 때문에 미확인 가설이 남을 수 있으며 최소 호출 경로를 수학적으로 보장하지는 않습니다.

**Q. 다음에 가장 먼저 개선할 부분은 무엇인가요?**

실제 모니터링과 프로파일러 연결, 입력 필터의 사람 라벨 평가, 다른 계열 Judge와 사람 평가의 비교입니다. 동일 조건의 호출량·토큰·지연시간도 계측하겠습니다.
