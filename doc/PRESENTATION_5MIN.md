# 5분 발표 대본과 화면 진행표

**발표자: SKALA 광주 2반 · G066 · 정준용**

**8장·총 300초** 구성이다. 전체 아키텍처는 5번 슬라이드 한 장으로 보여주고, 각 영역을 확대하는 슬라이드와 이동 효과는 사용하지 않는다. 좌우 120px 여백과 제목·본문·각주의 위치를 통일했다. 3번에서는 같은 첫 지표·경고의 두 사례를 비교해 가설 조사의 의미를 설명하고, 4번에서는 실제 조사 화면을 보여준다. 입력 validation은 2번의 보조 개선과 7번의 검증 항목으로 간략히 다룬다. 글꼴은 Noto Sans KR 계열 산세리프다.

## 직접 수정하는 방법

5번 슬라이드의 아키텍처는 사진 한 장으로 고정하지 않고 **8개 도형과 연결선**으로 구성했다. 각 상자의 문구·크기·색·위치를 직접 수정할 수 있다. 표와 본문도 편집할 수 있으며, 확대·이동 전환이나 자동 넘김은 없다.

발표는 PPT의 슬라이드 쇼에서 수동으로 넘긴다. 5번에서는 Vue, FastAPI, LangGraph의 주요 경로를 먼저 설명하고 LLM, MCP·RAG, SQLite, 평가·추적의 역할만 짚는다.

**대응 항목:** 프로젝트 소개

**발표 멘트**

**화면에서 짚을 부분**

프로젝트명과 소속을 소개한다. 오른쪽 사진은 실제 Ollama 실행 화면이다.

## 2. 해결 과제와 개선 이유 (30초)

**대응 항목:** 문제와 개선

**발표 멘트**

> 기존에는 업무 외 입력에도 모델을 호출했고, 경고만으로 원인을 추정하면 조치가 잘못될 수 있었습니다. 조회 실패와 수치 오류도 답변 신뢰도를 낮췄습니다. 그래서 호출 전 입력 검사, 가설을 구별하는 추가 관측, 성공 근거 보존과 사실 검증을 연결했습니다. 화면에는 결론뿐 아니라 판단이 달라진 이유도 남깁니다.

**화면에서 짚을 부분**

기존 문제와 개선 동작을 한 행씩 연결한다.

## 3. 추가 관측에 따라 달라지는 판단 (35초)

**대응 항목:** 핵심 개선 효과

**발표 멘트**

> 두 사례는 처음 CPU 91%와 배치 경고가 같았습니다. 하지만 한 사례는 배치 기여 86%와 중복 작업이 확인돼 배치 가설을 교차 지지했습니다. 다른 사례는 배치 기여가 5%여서 반증했고, 요청 처리 88%와 요청량 3.2배가 요청량 가설을 교차 지지했습니다. 같은 경고에서도 추가 관측에 따라 판단을 구별하는 것이 핵심입니다. 자료가 부족하거나 상충하면 보류합니다. 다음 장에서 그 조사 과정을 설명하겠습니다.

**화면에서 짚을 부분**

공통 첫 조회를 짚은 뒤 두 사례의 추가 관측과 판정을 비교한다. 단순 경고 조회와 가설을 구별하는 조사의 차이를 설명한다.

## 4. 가설을 구별하는 추가 조사 (60초)

**대응 항목:** 가설 기반 조사

**발표 멘트**

> 방금 요청량 사례에서 판단이 바뀐 과정을 화면으로 보겠습니다. 먼저 관측을 읽기 전에 가설별 지지와 반증 조건을 고정합니다. LLM은 아직 수행하지 않은 허용 질문 중에서 어떤 관측이 가설을 구별할지 선택합니다. MCP가 관측을 가져오면 코드는 정해진 수치 조건과 대조해 상태를 갱신합니다. 부족하면 다음 질문을 고르되 같은 5분 구간에서 최대 네 번만 조회합니다. 두 종류 관측이 한 가설을 지지하고 경쟁 가설이 반증되면 조기 종료하고, 관측이 없거나 상충하면 보류합니다. 화면에는 추가 조사 이유, 실제 관측, 판단 전후와 종료 이유를 함께 남깁니다. 현재 CPU 세 가설과 교육용 합성 관측에 적용했습니다.

**화면에서 짚을 부분**

왼쪽 네 처리 단계와 오른쪽 배치 반증·요청량 교차 지지 화면을 연결한다.

## 5. 전체 아키텍처 (50초)

**대응 항목:** 시스템 구조

**발표 멘트**

> 전체 구조는 이 한 장으로 설명하겠습니다. Vue 화면이 FastAPI에 질문을 전달하고 SSE로 진행 상황을 받습니다. 백엔드는 입력과 대상을 확인하고 LangGraph가 근거 수집과 가설 조사, 검증을 조정합니다. 실제 모델은 Ollama로 연결했고 OpenAI 연결도 지원합니다. MCP는 읽기 전용 관측 조회를, RAG는 매뉴얼 의미 검색을 담당합니다. SQLite에는 완료 결과와 근거, 대화 맥락을 저장합니다. 별도 Judge와 LangSmith는 품질 평가와 원격 추적을 담당합니다. 관측은 교육용 합성 데이터를 사용했습니다.

**화면에서 짚을 부분**

전체 아키텍처 한 장에서 Vue, FastAPI, LangGraph 경로와 연결된 도구·모델·기록·평가 역할을 짚는다.

## 6. 적용 기술과 역할 분리 (40초)

**대응 항목:** 적용 기술

**발표 멘트**

> 실행 중 사실 검사와 별도 품질 평가를 분리했습니다. LangGraph Supervisor는 전문 조회와 조건부 조사를 조정합니다. MCP는 조회 도구, 원문, 조사 절차를 표준 인터페이스로 제공합니다. RAG는 매뉴얼 여섯 종에서 관련 문서를 최대 세 개 검색합니다. 보고서는 수치와 출처, 허용 조치를 코드로 검사하며 세 번 실패하면 관측만 안내합니다. Judge와 LangSmith는 품질 평가와 추적을 담당합니다. 모듈화와 의존성 주입, 단위·API 테스트도 적용했습니다.

**화면에서 짚을 부분**

왼쪽에서 사실 검사와 품질 평가의 책임을 구분하고 오른쪽 기술별 역할을 설명한다.

## 7. 실제 LLM 검증 결과 (40초)

**대응 항목:** 실제 검증

**발표 멘트**

> 자동 테스트 99개를 통과했습니다. 입력 검사 도입 전 실제 Ollama의 가설 조사 기능은 6건 모두 통과했지만, Judge 포함 종합은 5건 통과였습니다. release 평가 실패도 보존했습니다. 입력 검사 도입 후 거절 다섯 건은 생성 0토큰과 LLM·MCP 미호출을 확인했습니다. LangSmith 실행 6건과 평가 점수 30개도 재조회했습니다. 수치는 10월 21일 보존 기록이며 전체 비용 절감률은 미측정입니다.

**화면에서 짚을 부분**

99개 테스트, 기능 6/6, Judge 포함 5/6을 짚고 아래 표에서 입력 검사와 이전 평가의 범위를 구분한다.

## 8. 한계와 다음 개선, 배운 점 (30초)

**대응 항목:** 교훈

**발표 멘트**

> 규칙 필터에는 오탐과 미탐이 있고, 현재 조사는 CPU 세 가설과 합성 관측에 한정됩니다. 실제 모니터링 연결, 사람과 다른 계열 Judge의 평가, 동일 조건의 비용 계측이 다음 과제입니다. 이번 경험으로 판단 조건과 근거를 남겨야 설명의 변화를 검증할 수 있다는 점을 배웠습니다. 교차 지지도 인과 확정과 구분하겠습니다.

**화면에서 짚을 부분**

남은 한계와 다음 개선을 연결하고 판단 조건과 근거를 기록한 경험으로 마무리한다.

## 시연과 시간 관리

4번 슬라이드의 실제 저장 화면에서 배치 기여 5% 반증, 요청 처리 기여 88%와 요청량 3.2배 교차 지지를 보여준다. 관측은 교육용 합성 데이터다. 전체 조사와 Judge 재평가는 발표 전에 끝낸 보존 결과를 사용한다.

3번은 같은 최초 관측에서 다른 판단이 나온 이유, 4번은 실제 조사 과정으로 연결한다. 입력 거절 실시간 시연은 5분 발표에서 생략하며, 입력 validation은 7번 검증 표에서 짧게 언급한다.

## 예상 질문과 답변

**Q. 기존 RAG나 추가 조회와 무엇이 다른가요?**

조회 전에 지지·반증 조건을 기록하고, 경쟁 가설을 구별할 질문을 선택합니다. 최종 답변뿐 아니라 판단이 달라진 이유와 종료 이유도 관측 근거로 남깁니다.

**Q. 실제 AI를 연결했나요? 실제 운영 데이터인가요?**

보존된 실측은 Ollama의 qwen3.5:2b로 계획·작성하고 qwen3:8b로 별도 평가했습니다. 지표·로그·추가 관측은 교육용 합성 데이터입니다. OpenAI 연결도 지원하지만 해당 저장 결과에는 사용하지 않았습니다.

**Q. Multi-Agent는 모든 역할이 각각 LLM인가요?**

지표·로그·런북 역할을 전문 서브그래프로 분리하고 Supervisor가 조정합니다. 전문 조회는 도구와 검색을 담당하며, 실제 LLM은 추가 질문 선택과 보고서 후보 작성에 사용합니다.

**Q. Vector DB는 무엇을 사용했나요?**

매뉴얼 6종에 맞춰 임베딩을 SQLite에 저장하고 NumPy 코사인 유사도로 검색하는 자체 영속 벡터 인덱스를 구현했습니다. Chroma나 FAISS 같은 외부 제품은 사용하지 않았습니다.

**Q. 0토큰이면 전체 비용을 줄였다는 뜻인가요?**

거절한 5건의 생성 토큰이 0이고 LLM·MCP 호출이 없음을 검증한 결과입니다. 전체 요청 대비 절감률과 하드웨어 비용까지 측정한 것은 아닙니다.

**Q. 기능 6/6인데 종합 평가는 왜 5/6인가요?**

릴리스 사례는 기능 조건을 충족했지만 Judge가 근거 점수를 낮게 준 검토 사례입니다. 기능과 의미 평가를 구분하고 원래 실패 점수를 보존했습니다. Judge 역시 오류 가능성이 있습니다.

**Q. 두 근거가 지지하면 원인을 확정할 수 있나요?**

현재 정책에서 교차 지지로 표시할 수 있지만 실제 인과관계 확정은 별도의 운영 검증이 필요합니다. 관측이 상충하거나 부족하면 판단을 보류합니다.

**Q. 왜 추가 조사를 최대 4회로 제한했나요?**

허용한 관측 종류가 네 가지이고 중복을 막아 호출량을 통제하기 위해서입니다. 한도 때문에 미확인 가설이 남을 수 있으며 최소 호출 경로를 수학적으로 보장하지는 않습니다.

**Q. 다음에 가장 먼저 개선할 부분은 무엇인가요?**

실제 모니터링과 프로파일러 연결, 입력 필터의 사람 라벨 평가, 다른 계열 Judge와 사람 평가의 비교입니다. 동일 조건의 호출량·토큰·지연시간도 계측하겠습니다.
