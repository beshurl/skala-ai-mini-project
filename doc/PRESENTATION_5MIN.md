## 구성 원칙

아키텍처 소개는 20초로 줄이고 추가 관측과 부분 실패 대응에 30초를 배정했다. 입력 validation은 11번의 보조 비용 통제로 짧게 설명한다. PPT와 Canva 발표자 노트는 아래 대본·연결 멘트·화면 진행으로 맞췄다. 산세리프와 통일된 여백을 유지하고 한 장에 설명을 더 밀어 넣지 않았다.

## 1. 가설 기반 운영 진단 에이전트 (15초)

**발표 멘트**

> 안녕하세요. SKALA 광주 2반 G066 정준용입니다. 기존 진단 흐름에 추가 조사와 근거 검증을 구현했습니다. 이번에 바꾼 기능과 실제 실행 결과를 중심으로 소개하겠습니다.

**슬라이드를 넘기면서**

> 먼저 기존 방식과 달라진 점입니다.

**화면에서 짚을 부분**

프로젝트명과 소속을 소개한다.

## 2. 이번에 바꾼 세 가지 흐름 (25초)

**발표 멘트**

> 기존에는 초기 경고를 원인으로 연결하기 쉽고, 답변 검사는 길이와 번호 형식에 머물렀습니다. 이번에는 경쟁 가설을 추가 관측으로 비교하고, 수치와 출처·조치 조건을 코드로 검사하도록 바꿨습니다. 최종 답변만 보여주던 화면에도 조사 이유와 판단 이력을 추가했습니다.

**슬라이드를 넘기면서**

> 이 세 변화를 전체 구조에서 짚어보겠습니다.

**화면에서 짚을 부분**

기존과 개선 열을 가로로 비교한다. 검증 수치의 전후 향상률을 측정한 표가 아니라 구현 동작 비교다.

## 3. 개선 기능을 연결한 전체 구조 (20초)

**발표 멘트**

> 전체 구조에서는 바꾼 부분만 보겠습니다. LangGraph에 추가 조사와 검증 반복을 연결하고, MCP에는 추가 관측 도구를 연결했습니다. 화면에는 판단 이력을, 저장과 평가에는 근거 기록을 추가했습니다. 모델·도구·검색기는 의존성 주입으로 분리했습니다.

**슬라이드를 넘기면서**

> 가장 핵심인 추가 조사부터 설명하겠습니다.

**화면에서 짚을 부분**

중앙의 추가 조사·검증, 왼쪽 판단 이력, 아래 관측·검색, 위 평가만 짚는다. Vue·FastAPI·MCP 자체를 새로 만든 기술이라고 설명하지 않는다.

## 4. 원인 추정에 반증 절차 추가 (35초)

**발표 멘트**

> 중복 배치 경고가 있어도 실제 CPU를 쓰는 작업은 다를 수 있습니다. 그래서 조회 전에 지지·반증 조건을 고정했습니다. 예를 들어 작업군의 CPU 기여 70% 이상은 지지, 15% 이하는 반증입니다. LLM은 남은 질문을 고르고 코드는 관측을 판정합니다. 두 관측의 교차 지지와 경쟁 가설의 반증을 확보하면 종료하고, 최대 네 번 뒤에도 불충분하면 판단을 보류합니다.

**슬라이드를 넘기면서**

> 이 조사 과정도 화면에서 확인할 수 있게 했습니다.

**화면에서 짚을 부분**

사전 조건, 질문 선택, 코드 판정 순으로 설명한다. 70%는 실험용 작업군 기여 기준이며 전체 CPU 경고 임계값과 구분한다.

## 5. 조사 이유와 판단 변화 표시 (30초)

**발표 멘트**

> 결과만 보는 대신 왜 조사했고 무엇이 바뀌었는지 확인하도록 화면을 추가했습니다. 실제 실행의 결과 영역입니다. 배치 가설은 반증됐고 요청량 가설은 교차 지지로 바뀌었습니다. 과정 패널에는 조회 이유와 사전 조건, 관측과 종료 이유도 남깁니다. 사용자가 결론의 근거를 직접 따라갈 수 있게 한 변화입니다.

**슬라이드를 넘기면서**

> 관측을 바꿨을 때 실제 판단도 달라지는지 비교했습니다.

**화면에서 짚을 부분**

화면의 반증·교차 지지와 근거 ID를 짚는다. 발췌 영역 밖의 조사 이유·사전 조건은 원본 전체 화면과 저장 이력에서 확인한다.

## 6. 같은 경고에서 달라진 판단 (35초)

**발표 멘트**

> 두 사례는 최초 CPU 91%와 중복 배치 경고가 같습니다. 왼쪽은 배치 CPU 기여 86%와 작업 중첩이 확인돼 배치 가설을 지지했습니다. 오른쪽은 배치 기여 5%와 요청량 3.2배 증가를 확인해 요청량 가설을 지지했습니다. 둘 다 개선 버전의 실행이며, 이전 버전과의 성능 비교는 아닙니다. 실제 LLM을 사용했고 관측은 합성 데이터입니다.

**슬라이드를 넘기면서**

> 추가 조회에 실패했을 때도 결과를 지키도록 바꿨습니다.

**화면에서 짚을 부분**

추가 관측과 판단의 차이를 짚는다. 두 개선 실행 사례를 버전 전후 측정이나 운영 장애 정답률로 설명하지 않는다.

## 7. 추가 관측과 부분 실패 대응 (30초)

**발표 멘트**

> 기존 조회 흐름에 가설별 추가 관측 도구를 연결했습니다. 동시에 일부 도구가 실패하면 성공한 근거까지 잃지 않도록 실패를 항목별로 격리했습니다. 실제 LLM 평가에서는 CPU 귀속 도구의 타임아웃을 주입했습니다. 다른 관측은 유지했고, 원인 확정에 필요한 근거가 없으므로 판단을 보류했습니다. 실패를 숨기지 않고 진단 한계를 남기는 것이 목표입니다.

**슬라이드를 넘기면서**

> 문서 검색도 수집한 관측을 활용하도록 바꿨습니다.

**화면에서 짚을 부분**

추가 관측 도구와 부분 실패 처리를 설명하고 타임아웃 주입 사례의 성공 근거 유지·판단 보류를 짚는다.

타임아웃 검증 원본: [probe-failure 사례](../artifacts/investigation_evaluation.json). `partial_retained=true`, `outcome=판단 보류`를 확인한다.

## 8. 단일 런북 선택에서 다중 검색으로 (25초)

**발표 멘트**

> 기존 키워드 분류로 한 런북을 고르던 흐름을 의미 검색으로 바꿨습니다. 질문에 지표와 알림을 더해 매뉴얼 여섯 종에서 최대 세 종을 찾습니다. SQLite에 벡터를 저장하고 NumPy로 유사도를 계산합니다. 검색 후보는 MCP 원문과 대조하며, 실제 조치는 관측 조건에 맞는 근거만 사용합니다.

**슬라이드를 넘기면서**

> 이 근거가 보고서에 올바르게 쓰였는지도 검사합니다.

**화면에서 짚을 부분**

기존 단일 선택과 개선 다중 검색의 동작을 비교한다. 검색 정확도 향상률은 제시하지 않는다.

## 9. 형식 검사에서 사실 검증으로 (30초)

**발표 멘트**

> 기존 길이·번호 검사를 시스템명, 수치, 근거와 조치 조건까지 확장했습니다. 오른쪽은 실제 Ollama 재실행 결과입니다. 첫 초안은 다음 행동이 누락돼 불합격했고 두 번째 작성에서 보완해 통과했습니다. 화면에도 작성 두 회와 재작성 한 회가 남습니다. 최대 세 번 뒤에도 실패하면 검증 미통과를 알리고 관측 사실만 안내합니다.

**슬라이드를 넘기면서**

> 실행 중 검사와 별도로 답변 품질 평가도 추가했습니다.

**화면에서 짚을 부분**

여섯 검사 항목과 작성 2회·재작성 1회를 짚는다. 1차 누락은 저장 이벤트 근거이며 화면은 최종 통과 상태다.

## 10. 기능 검사에 Judge 평가 추가 (35초)

**발표 멘트**

> 기능 동작과 답변 품질을 분리해 평가했습니다. 실제 LLM 여섯 사례는 보류와 실패 대응을 포함한 기능 검사를 모두 통과했습니다. 별도 Judge의 다섯 항목까지 포함하면 다섯 건 통과입니다. 릴리스 사례는 주장 대조 단계의 Judge 오판을 검토 중이며 미통과를 그대로 보존했습니다. 자동 테스트 99개와 실제 모델 여섯 건 평가도 구분했습니다.

**슬라이드를 넘기면서**

> 이 평가가 원격에 저장됐는지도 직접 확인했습니다.

**화면에서 짚을 부분**

기능 6/6과 Judge 포함 5/6, release 최종 근거 점수 2/5를 비교한다. Judge 오류는 원점수와 주장 대조 결과를 보존한 검토 사항이다.

## 11. 실행 기록과 비용 통제 추가 (20초)

**발표 멘트**

> LangSmith에 저장한 실행 여섯 건과 점수 서른 개를 다시 조회했습니다. 별도로 모델 호출 전 입력 검사도 추가해 거절 다섯 건의 LLM·MCP 호출과 생성 토큰이 0임을 확인했습니다. 이는 거절 요청의 결과이며 전체 비용 절감률은 아직 측정하지 않았습니다.

**슬라이드를 넘기면서**

> 마지막으로 개선의 한계와 다음 과제입니다.

**화면에서 짚을 부분**

6건·30개 재조회와 별도 입력 거절 0토큰만 짚는다. 두 검증 시점을 구분한다.

## 12. 개선 효과와 남은 과제 (30초)

**발표 멘트**

> 현재는 CPU 세 가설과 합성 관측에 한정됩니다. 조회 한도는 비용을 통제하지만 미확인 가설을 남길 수 있고, Judge도 오판할 수 있습니다. 다음에는 실제 모니터링과 다른 계열 모델·사람 평가를 연결하겠습니다. 이번 작업을 통해 결론뿐 아니라 판단 조건과 근거를 함께 남겨야 진단이 달라진 이유까지 설명할 수 있다는 점을 배웠습니다. 감사합니다.

**화면에서 짚을 부분**

실제 데이터 연결, 질문 우선순위, 다른 Judge·사람 평가를 한계와 연결한다.

## 시연과 시간 관리

5번은 추가한 화면, 6번은 관측에 따른 판단 차이, 7번은 실패 시의 동작, 9번은 실제 재작성 결과, 10~11번은 평가와 저장 검증에 집중한다. 같은 수치를 반복해 읽지 않는다. 발표 현장에서 전체 LLM 조사나 Judge를 재실행하지 않고 보존된 실제 기록을 보여준다.

발표 속도에 따라 약 5분 30초 전후로 달라질 수 있다. 여유가 없으면 3번 구조 소개와 8번 저장 구현을 짧게 하고 조사·검증 결과를 우선한다.

## 예상 질문과 답변

**Q. 이번에 수정·추가한 부분과 원래 기반 기능은 어떻게 구분하나요?**

기존 코드의 계획·조회·작성과 MCP 연결을 바탕으로 추가 조사 루프, 조회 전 판정 조건, 사실 검증·제한 답변, 판단 이력 화면, 관측 기반 다중 검색, 부분 실패 격리와 평가·추적 검증을 개선했습니다. Vue·FastAPI·MCP라는 기술 자체를 신규 기능으로 주장하지 않습니다. 2·7·8페이지는 구현 동작의 전후 비교이고, 6페이지는 개선 버전 안에서 추가 관측을 달리한 두 실행입니다.

**Q. 개선 전후 정확도 향상률도 실측한 건가요?**

이 발표의 실제 수치는 개선된 조사 흐름의 여섯 사례와 별도 입력 거절 검증입니다. 동일한 실제 LLM 조건으로 기존·개선 버전의 운영 정확도 향상률을 측정한 수치로 제시하지 않습니다. 기존 코드와 현재 동작의 차이를 구분하고, 저장한 실제 실행으로 개선 기능의 동작을 확인했습니다.

**Q. 왜 조회 전에 판정 조건을 정했나요?**

관측 결과를 보고 설명에 맞게 기준을 바꾸는 것을 막기 위해서입니다. 조건과 원본 관측, 상태 변경을 함께 남기면 같은 경고에서 결론이 달라진 이유를 검토할 수 있습니다. 현재의 세 가설·네 관측 범위에서 동작하며 새로운 원인을 자유롭게 발명하는 기능은 아닙니다.

**Q. 기존 RAG나 추가 조회와 무엇이 다른가요?**

조회 전에 지지·반증 조건을 기록하고, 경쟁 가설을 구별할 질문을 선택합니다. 최종 답변뿐 아니라 판단이 달라진 이유와 종료 이유도 관측 근거로 남깁니다.

**Q. 실제 AI를 연결했나요? 실제 운영 데이터인가요?**

보존된 실측은 Ollama의 qwen3.5:2b로 계획·작성하고 qwen3:8b로 별도 평가했습니다. 지표·로그·추가 관측은 교육용 합성 데이터입니다. OpenAI 연결도 지원하지만 해당 저장 결과에는 사용하지 않았습니다.

**Q. Multi-Agent는 모든 역할이 각각 LLM인가요?**

지표·로그·런북 역할을 전문 서브그래프로 분리하고 Supervisor가 조정합니다. 전문 조회는 도구와 검색을 담당하며, 실제 LLM은 추가 질문 선택과 보고서 후보 작성에 사용합니다.

**Q. Vector DB는 무엇을 사용했나요?**

매뉴얼 6종에 맞춰 임베딩을 SQLite에 저장하고 NumPy 코사인 유사도로 검색하는 자체 영속 벡터 인덱스를 구현했습니다. Chroma나 FAISS 같은 외부 제품은 사용하지 않았습니다.

**Q. 0토큰이면 전체 비용을 줄였다는 뜻인가요?**

거절한 5건의 생성 토큰이 0이고 LLM·MCP 호출이 없음을 검증한 결과입니다. 전체 요청 대비 절감률과 하드웨어 비용까지 측정한 것은 아닙니다.

**Q. 기능 6/6인데 종합 평가는 왜 5/6인가요?**

여섯 사례는 예상된 가설 상태, 조회 한도, 중복 방지, 보류와 부분 실패 대응 등 기능 조건을 모두 충족했습니다. 종합 통과에는 별도 Judge의 다섯 항목이 각각 4/5 이상이어야 합니다. release의 전체 답변 원점수는 5점이었지만 별도 주장 대조가 지지·반증 조건을 혼동해 모순으로 판단했고, 코드의 상한 정책으로 최종 근거 점수가 2/5가 됐습니다. 원점수·주장 대조·최종 미통과를 모두 보존한 Judge 오판 검토 사례입니다. 6/6은 원인 확정 여섯 건이나 운영 정확도 100%를 뜻하지 않습니다.

**Q. 두 근거가 지지하면 원인을 확정할 수 있나요?**

현재 정책에서 교차 지지로 표시할 수 있지만 실제 인과관계 확정은 별도의 운영 검증이 필요합니다. 관측이 상충하거나 부족하면 판단을 보류합니다.

**Q. 왜 추가 조사를 최대 4회로 제한했나요?**

허용한 관측 종류가 네 가지이고 중복을 막아 호출량을 통제하기 위해서입니다. 한도 때문에 미확인 가설이 남을 수 있으며 최소 호출 경로를 수학적으로 보장하지는 않습니다.

**Q. 다음에 가장 먼저 개선할 부분은 무엇인가요?**

실제 모니터링과 프로파일러 연결, 입력 필터의 사람 라벨 평가, 다른 계열 Judge와 사람 평가의 비교입니다. 동일 조건의 호출량·토큰·지연시간도 계측하겠습니다.

## 검증 결과의 출처와 해석 범위

가설 비교와 Judge·추적은 2026년 10월 21일 보존 기록, 보고서 재작성 화면은 10월 22일 실제 재실행이다. 이번 발표 구성 수정에서는 모델·Judge 평가와 자동 테스트를 재실행하지 않았다.

- [입력 validation 원본](../artifacts/input_validation_verification.json): 거절 5건 생성 0토큰, LLM·MCP 0회, 테스트 99개 통과.
- [가설 조사 평가 원본](../artifacts/investigation_evaluation.json): 입력 검사 도입 전 평가. 기능 6/6, Judge 포함 종합 5/6, 원격 실행 6건·평가 점수 30개 재조회.
- [추가 조사 저장 화면](../artifacts/screenshots/investigation-traffic-desktop.png): 실제 Ollama 계획·작성, 합성 관측에서 가설 변경.

Judge는 별도 품질 평가다. 모든 전문 조회가 독립적인 LLM은 아니며 RAG는 SQLite 영속 벡터와 NumPy 검색이다. SQLite는 완료 결과와 후속 맥락을 복원하고 실행 중 그래프 체크포인트 재개는 지원하지 않는다.
