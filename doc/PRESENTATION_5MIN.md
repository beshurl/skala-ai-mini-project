## 같은 그림 안에서 이동하는 순서

| 전환 | 카메라가 보는 영역 | 설명할 내용 |

| 3 → 4 | 전체 그림에서 가운데 BACKEND 확대 | FastAPI, 로컬 입력 검사, 생성 0토큰, 대상·맥락 |
| 4 → 5 | 같은 원본의 왼쪽 FRONTEND로 이동 | Vue, SSE 진행, 조사 이유와 판단 전후, 완료 기록 복원 |

최신 PPTX는 **PowerPoint 변환(Morph)**을 파일 안에 저장한다. 3→4, 4→5, 5→6, 6→7의 네 구간에 각각 1.4초를 적용했다. 같은 원본을 공유하는 사진 객체의 이름을 `!!ArchitectureCamera`로 연결해 위치·크기·자르기 영역을 이어준다. 그림은 PPTX 내부에 포함되므로 Canva 접속 없이 발표한다.

### 오프라인 발표 방법

1. 위의 최신 PPT를 PC에 다운로드하고, Morph를 지원하는 데스크톱 PowerPoint에서 연다. Microsoft 365 또는 PowerPoint 2021/2024를 권장한다.
2. 일반 편집 화면 대신 **슬라이드 쇼**로 시작한다. 발표자 보기에서 대본을 함께 확인할 수 있다.
3. 3장의 전체 구조에서 다음 슬라이드로 이동하면 백엔드가 확대된다. 이후 왼쪽 프론트엔드, 오른쪽 AI, 위쪽 평가 영역으로 이동한다.
4. 전환 후에는 화면이 멈춘다. 발표 멘트에 맞춰 클릭이나 오른쪽 방향키로 넘기며, 자동 넘김은 사용하지 않는다.
5. Canva에서 다시 내려받은 파일 대신 이 저장소의 최신 PPTX를 사용한다. Canva 편집본은 별도로 유지하며, 다시 내보내면 PowerPoint 전용 효과가 보존되지 않을 수 있다.

호환성: Morph를 지원하지 않는 뷰어는 기본 페이드로 표시할 수 있다. 지원 버전과 객체 연결 규칙은 [Microsoft 안내](https://support.microsoft.com/en-us/powerpoint/morph-transition-tips-and-tricks)를 따른다.

검증 범위: 9장 렌더링과 수정 전후 화면 비교, 네 Morph 설정·1.4초 시간·단일 원본 이미지 연결, 본문·발표자 노트 보존, 외부 이미지 의존성 없음을 확인했다. 현재 작업 환경에는 PowerPoint 앱이 없어 실제 PowerPoint 슬라이드쇼 재생은 미확인이다.

## 2. 해결 과제와 개선 이유 (30초)

**대응 항목:** 2) 문제 개선 및 신규 구현 사항

**발표 멘트**

> 첫째, 업무 외 입력에도 모델을 호출해 토큰이 낭비됐습니다. 둘째, CPU 상승과 경고만으로 원인을 추정하면 잘못된 조치를 권할 수 있었습니다. 셋째, 문서와 조회 결과가 불완전하거나 수치가 틀려도 답변을 신뢰하기 어려웠습니다. 그래서 호출 전 입력 검사, 가설을 구별하는 추가 조사, 근거 수집과 사실 검증을 연결했습니다. 화면에는 결과뿐 아니라 판단이 달라진 이유도 보여줍니다.

**화면에서 짚을 부분**

문제·개선 이유·구현의 세 열을 연결한다. 다음 장 전체 지도에서 각 개선이 어디에 배치되는지 보겠다고 전환한다.

## 3. 전체 아키텍처 (25초)

**대응 항목:** 3) 적용 기술 요소 / 4) 구현 결과

**발표 멘트**

> 우리 프로젝트의 기술과 연결을 한 장의 그림으로 정리했습니다. 왼쪽 Vue 화면이 가운데 FastAPI 백엔드와 HTTP와 SSE로 통신하고, 오른쪽 LangGraph가 조사 흐름을 조정합니다. 아래 SQLite는 결과와 맥락을 저장합니다. 위에는 실제 Ollama 모델과 별도 Judge, LangSmith가 있습니다. 이제 이 그림의 백엔드부터 확대하겠습니다.

**화면에서 짚을 부분**

Vue, FastAPI, LangGraph와 연결선을 짚는다. SQLite, Ollama, Judge와 LangSmith를 짧게 소개한 뒤 같은 그림에서 가운데 백엔드로 확대한다.

## 4. 백엔드 확대: 호출 전 입력 검사 (25초)

**대응 항목:** 2) 핵심 개선 / 3) FastAPI·입력 validation

**발표 멘트**

> 첫 번째 영역은 백엔드 입력 검사입니다. 반복 문자나 명백한 업무 외 요청은 로컬 규칙으로 거절해 모델과 도구가 실행되기 전에 종료합니다. 통과한 입력은 등록 대상과 이전 대화 맥락을 확인합니다. 대상이 모호하면 되묻고 짧은 후속 답변도 보존합니다. 검증한 거절 다섯 건은 생성 0토큰이었습니다.

**화면에서 짚을 부분**

가운데 BACKEND 영역의 FastAPI 로고, 입력 validation, 생성 0토큰과 대상·맥락 확인을 짚는다. 다음 장에서 같은 그림의 왼쪽 Vue로 이동한다.

## 5. 프론트엔드 확대: 조사 이유와 과정 (30초)

**대응 항목:** 2) 신규 화면 / 3) Vue 3·SSE·기록 복원

**발표 멘트**

> 같은 그림의 왼쪽 Vue 화면입니다. 단순한 최종 답변 외에 추가 조사의 이유, 조회 전에 정한 조건, 관측값과 가설의 판단 전후를 보여줍니다. SSE 이벤트로 단계별 진행과 일부 조회 실패를 전달하고 성공한 근거는 유지합니다. 완료 결과와 근거, 토큰 사용량과 후속 대화 맥락은 SQLite에서 복원합니다. 실행 중 그래프의 체크포인트 재개까지 구현한 것은 아닙니다.

**화면에서 짚을 부분**

원본 그림이 왼쪽으로 이동하며 Vue 프론트엔드를 확대한다. 조사 이유, 판단 전후, SSE, 기록 복원을 짚는다.

## 6. AI 확대: 근거 수집과 가설 조사 (60초)

**대응 항목:** 3) LangGraph·전문 서브그래프·MCP·RAG

**발표 멘트**

> 이제 같은 그림의 오른쪽 AI 영역입니다. LangGraph Supervisor가 지표와 로그 전문 조회를 병렬로 조정합니다. 관측을 반영한 RAG는 여섯 매뉴얼의 임베딩을 SQLite에 저장하고 코사인 유사도로 최대 세 개를 검색합니다. MCP의 Tool은 관측 조회, Resource는 런북 원문, Prompt는 조사 절차를 제공합니다. 핵심은 추가 조회 전에 가설별 지지와 반증 조건을 기록하는 점입니다. 실제 LLM은 허용된 미수행 질문을 선택하고, 코드는 같은 5분 구간의 관측으로 가설을 판정합니다. 부족하면 다시 질문을 고르되 최대 네 번 조회합니다. 두 관측의 교차 지지와 경쟁 가설 반증이면 조기 종료하고 상충하면 보류합니다. 전문 조회가 모두 별도 LLM인 것은 아닙니다.

**화면에서 짚을 부분**

원본 오른쪽 AI를 확대한다. LangGraph와 병렬 조회, RAG, 사전 조건·질문 선택·관측·판정 반복선, MCP 인터페이스를 짚는다.

## 7. 평가 확대: 검증과 원격 추적 (35초)

**대응 항목:** 3) 코드 품질·LLM-as-a-Judge·LangSmith

**발표 멘트**

> 마지막으로 그림 위쪽의 평가 영역입니다. 실행 중에는 LCEL로 보고서 후보를 작성한 뒤 대상과 수치, 출처와 허용 조치를 코드로 검사합니다. 세 번 작성해도 실패하면 확인한 관측만 제공합니다. 별도 Judge는 근거 충실성 등 다섯 기준을 평가하고, LangSmith는 실행 단계와 토큰, 점수를 기록합니다. 원격 실행과 평가 점수를 다시 조회해 추적 여부도 확인했습니다. 모듈화와 의존성 주입, 단위·API 테스트로 이 책임들을 분리해 검증했습니다.

**화면에서 짚을 부분**

원본 위쪽 Judge와 LangSmith를 확대한다. 발표 문구에서 런타임 사실 검사와 별도 품질 평가를 구분한다. 다음 장의 실제 화면과 수치로 검증 결과를 연결한다.

## 8. 실행 화면과 실제 검증 결과 (45초)

**대응 항목:** 4) 구현 결과

**발표 멘트**

> 실제 모델로 실행해 저장한 화면입니다. CPU 91%와 배치 경고가 같아도 배치의 CPU 기여가 5%여서 배치 가설은 반증했습니다. 요청 처리 기여 88%와 요청량 3.2배는 요청량 가설을 교차 지지했습니다. 관측은 교육용 합성 데이터입니다. 오른쪽은 10월 21일 기록으로, 입력 거절 다섯 건의 생성 0토큰과 LLM·MCP 미호출, 테스트 99개 통과를 확인했습니다. 입력 검사 도입 전 실제 가설 평가는 기능 6/6, Judge 포함 종합 5/6이었고 원격 실행 6건과 점수 30개도 재조회했습니다.

**화면에서 짚을 부분**

배치 반증과 요청량 교차 지지의 실제 저장 화면을 짚는다. 오른쪽 검증 표에서 입력 거절과 이전 가설 조사 평가를 구분한다. 전체 조사나 Judge는 재실행하지 않는다.

## 9. 한계와 다음 개선, 배운 점 (35초)

**대응 항목:** 5) 교훈

**발표 멘트**

> 입력 규칙에는 오탐과 미탐이 생길 수 있습니다. 추가 조사는 CPU 세 가설과 합성 관측에 한정되고 최대 네 번의 조회 때문에 미확인 가설도 남을 수 있습니다. 교차 지지는 인과 확정과 구분해야 하며 Judge에도 오류와 편향이 있습니다. 다음에는 실제 모니터링, 사람과 다른 계열 Judge의 교차 평가, 동일 조건의 전체 비용 측정을 진행하겠습니다. 이번 경험으로 자연스러운 설명보다 판단 조건과 근거를 남기는 일이 중요함을 배웠습니다. 결론 보류에도 이유를 보여주는 설계를 이어가겠습니다.

**화면에서 짚을 부분**

한계와 다음 개선을 연결한다. 판단 조건과 근거를 남기는 설계 경험으로 마무리하고 5분에 종료한다.

## 시연 순서와 시간 관리

PPT 안에서 발표한다. 전체 그림과 백엔드·프론트엔드·AI·평가 확대 화면을 설명하고, 8장의 저장된 실제 실행 화면으로 가설 판단 변경을 보여준다. 실제 조사와 Judge는 발표 전에 실행한 보존 결과를 사용한다.

실시간 시연을 요구받으면 8장 시간 안에서 시스템 선택 후 `오늘 날씨 알려줘`를 입력해 거절 이유와 생성 0토큰만 확인한다. 서버가 준비되지 않았다면 [저장된 입력 거절 화면](../artifacts/screenshots/input-rejected-zero-tokens.png)을 사용하고 표 설명 시간을 줄인다.

추가 조사의 별도 시연은 발표 전후에 진행한다. 사전 조건, 배치 기여 5% 반증, 요청 처리 기여 88%·요청량 3.2배 교차 지지를 순서대로 보여준다. 관측은 교육용 합성 데이터이며 교차 지지는 인과 확정과 구분한다.

## 예상 질문과 답변

**Q. 기존 RAG나 추가 조회와 무엇이 다른가요?**

조회 전에 지지·반증 조건을 기록하고, 경쟁 가설을 구별할 질문을 선택합니다. 최종 답변뿐 아니라 판단이 달라진 이유와 종료 이유도 관측 근거로 남깁니다.

**Q. 실제 AI를 연결했나요? 실제 운영 데이터인가요?**

보존된 실측은 Ollama의 qwen3.5:2b로 계획·작성하고 qwen3:8b로 별도 평가했습니다. 지표·로그·추가 관측은 교육용 합성 데이터입니다. OpenAI 연결도 지원하지만 해당 저장 결과에는 사용하지 않았습니다.

**Q. Multi-Agent는 모든 역할이 각각 LLM인가요?**

지표·로그·런북 역할을 전문 서브그래프로 분리하고 Supervisor가 조정합니다. 전문 조회는 도구와 검색을 담당하며, 실제 LLM은 추가 질문 선택과 보고서 후보 작성에 사용합니다.

**Q. Vector DB는 무엇을 사용했나요?**

매뉴얼 6종에 맞춰 임베딩을 SQLite에 저장하고 NumPy 코사인 유사도로 검색하는 자체 영속 벡터 인덱스를 구현했습니다. Chroma나 FAISS 같은 외부 제품은 사용하지 않았습니다.

**Q. 0토큰이면 전체 비용을 줄였다는 뜻인가요?**

거절한 5건의 생성 토큰이 0이고 LLM·MCP 호출이 없음을 검증한 결과입니다. 전체 요청 대비 절감률과 하드웨어 비용까지 측정한 것은 아닙니다.

**Q. 기능 6/6인데 종합 평가는 왜 5/6인가요?**

릴리스 사례는 기능 조건을 충족했지만 Judge가 근거 점수를 낮게 준 검토 사례입니다. 기능과 의미 평가를 구분하고 원래 실패 점수를 보존했습니다. Judge 역시 오류 가능성이 있습니다.

**Q. 두 근거가 지지하면 원인을 확정할 수 있나요?**

현재 정책에서 교차 지지로 표시할 수 있지만 실제 인과관계 확정은 별도의 운영 검증이 필요합니다. 관측이 상충하거나 부족하면 판단을 보류합니다.

**Q. 왜 추가 조사를 최대 4회로 제한했나요?**

허용한 관측 종류가 네 가지이고 중복을 막아 호출량을 통제하기 위해서입니다. 한도 때문에 미확인 가설이 남을 수 있으며 최소 호출 경로를 수학적으로 보장하지는 않습니다.

**Q. 다음에 가장 먼저 개선할 부분은 무엇인가요?**

실제 모니터링과 프로파일러 연결, 입력 필터의 사람 라벨 평가, 다른 계열 Judge와 사람 평가의 비교입니다. 동일 조건의 호출량·토큰·지연시간도 계측하겠습니다.

## 검증 결과의 출처와 해석 범위

수치는 2026년 10월 21일 보존 기록이며 이번 발표 구성 변경을 위한 모델 재평가는 실행하지 않았다.

- [입력 validation 원본](../artifacts/input_validation_verification.json): 거절 5건 생성 0토큰, LLM·MCP 0회, 테스트 99개 통과.
- [가설 조사 평가 원본](../artifacts/investigation_evaluation.json): 입력 검사 도입 전 평가. 기능 6/6, Judge 포함 종합 5/6, 원격 실행 6건·평가 점수 30개 재조회.
- [추가 조사 저장 화면](../artifacts/screenshots/investigation-traffic-desktop.png): 실제 Ollama 계획·작성, 합성 관측에서 가설 변경.

Judge는 별도 품질 평가다. 모든 전문 조회가 독립적인 LLM은 아니며 RAG는 SQLite 영속 벡터와 NumPy 검색이다. SQLite는 완료 결과와 후속 맥락을 복원하고 실행 중 그래프 체크포인트 재개는 지원하지 않는다.
