## 직접 수정하는 방법

5번 슬라이드의 아키텍처는 사진 한 장으로 고정하지 않고 **8개 도형과 연결선**으로 구성했다. 각 상자의 문구·크기·색·위치를 직접 수정할 수 있다. 표와 본문도 편집할 수 있으며, 확대·이동 전환이나 자동 넘김은 없다.

발표는 PPT의 슬라이드 쇼에서 수동으로 넘긴다. 5번에서는 Vue, FastAPI, LangGraph의 주요 경로를 먼저 설명하고 LLM, MCP·RAG, SQLite, 평가·추적의 역할만 짚는다.

## 1. 가설 기반 운영 진단 에이전트 (15초)

**대응 항목:** 1) 표지 및 소속 정보

**발표 멘트**

> 안녕하세요. SKALA 광주 2반 G066 정준용입니다. 장애 질문에 답하는 운영 진단 에이전트에 입력 검사와 가설 기반 추가 조사를 구현했습니다. 핵심 기능, 전체 구조, 실제 검증 결과 순서로 설명하겠습니다.

**화면에서 짚을 부분**

프로젝트명과 소속을 소개한다.

## 2. 해결 과제와 개선 이유 (30초)

**대응 항목:** 2) 문제 개선 및 신규 구현 사항

**발표 멘트**

> 첫째, 업무 외 입력에도 모델을 호출해 토큰이 낭비됐습니다. 둘째, CPU 상승과 경고만으로 원인을 추정하면 잘못된 조치를 권할 수 있었습니다. 셋째, 문서와 조회 결과가 불완전하거나 수치가 틀려도 답변을 신뢰하기 어려웠습니다. 그래서 호출 전 입력 검사, 가설을 구별하는 추가 조사, 근거 수집과 사실 검증을 연결했습니다. 화면에는 결과뿐 아니라 판단이 달라진 이유도 보여줍니다.

**화면에서 짚을 부분**

업무 외 입력, 근거가 부족한 원인 추정, 조회 실패와 수치 오류를 각각의 개선과 연결한다.

## 3. 입력 validation으로 호출 전 차단 (35초)

**대응 항목:** 2) 핵심 개선 기능

**발표 멘트**

> 입력 검사는 모델을 부르기 전에 백엔드에서 실행합니다. 반복 문자나 명백한 업무 외 요청을 로컬 규칙으로 거절합니다. 등록된 대상이 불분명하면 추가 질문을 하고, 짧은 후속 답변은 원래 질문과 연결합니다. 거절 입력은 저장하지 않아 맥락이 오염되는 것도 막았습니다. 실제 서버에 보낸 거절 다섯 건은 생성 0토큰이었고 LLM과 MCP 호출도 없었습니다. 전체 서비스의 비용 절감률까지 측정한 것은 아닙니다.

**화면에서 짚을 부분**

입력별 처리와 생성 0토큰의 검증 범위를 짚는다.

## 4. 가설을 구별하는 추가 조사 (50초)

**대응 항목:** 2) 신규 구현 기능

**발표 멘트**

> 핵심 차별점은 조회 전에 지지와 반증 조건을 정하는 점입니다. 실제 LLM은 허용된 질문 중 아직 하지 않은 질문을 고릅니다. MCP가 추가 관측을 읽으면 코드는 같은 5분 구간의 수치로 가설을 판정합니다. 부족하면 다음 질문을 고르되 전체 조회는 네 번으로 제한합니다. 두 관측이 한 가설을 지지하고 경쟁 가설이 반증되면 조기 종료하며, 자료가 부족하거나 상충하면 판단을 보류합니다. 프론트에는 조사 이유, 관측값과 판단 전후를 보여줍니다. 현재는 CPU 장애의 세 가설과 교육용 합성 관측에 적용합니다.

**화면에서 짚을 부분**

조건 설정, 질문 선택, 관측 대조, 종료 판정을 표 순서로 설명한다.

## 5. 전체 아키텍처 (50초)

**대응 항목:** 3) 적용 기술 요소 / 4) 구현 결과

**발표 멘트**

> 전체 구조는 이 한 장으로 설명하겠습니다. Vue 화면이 FastAPI에 질문을 전달하고 SSE로 진행 상황을 받습니다. 백엔드는 입력과 대상을 확인하고 LangGraph가 근거 수집과 가설 조사, 검증을 조정합니다. 실제 모델은 Ollama로 연결했고 OpenAI 연결도 지원합니다. MCP는 읽기 전용 관측 조회를, RAG는 매뉴얼 의미 검색을 담당합니다. SQLite에는 완료 결과와 근거, 대화 맥락을 저장합니다. 별도 Judge와 LangSmith는 품질 평가와 원격 추적을 담당합니다. 관측은 교육용 합성 데이터를 사용했습니다.

**화면에서 짚을 부분**

전체 구조에서 Vue, FastAPI, LangGraph 경로를 짚고 LLM, MCP·RAG, SQLite, 평가·추적의 역할만 설명한다.

## 6. 적용 기술과 역할 분리 (40초)

**대응 항목:** 3) 적용 기술 요소

**발표 멘트**

> LangGraph Supervisor가 지표와 로그, 런북 전문 조회를 조정합니다. 전문 조회가 모두 별도 LLM인 것은 아닙니다. MCP는 조회 Tool, 런북 원문 Resource, 조사 절차 Prompt를 제공합니다. RAG는 매뉴얼 여섯 종을 임베딩해 SQLite에 저장하고 NumPy 코사인 유사도로 최대 세 개를 검색합니다. LCEL 작성 결과는 대상과 수치, 출처와 허용 조치를 코드로 검사합니다. 최대 세 번 작성해도 실패하면 확인한 관측만 안내합니다. 별도 Judge와 LangSmith, 모듈화와 의존성 주입, 단위·API 테스트로 품질과 실행 과정을 확인했습니다.

**화면에서 짚을 부분**

기술 표에서 MCP·RAG, 사실 검사와 별도 평가, 코드 품질의 책임을 짚는다.

## 7. 실행 화면과 실제 검증 결과 (45초)

**대응 항목:** 4) 구현 결과

**발표 멘트**

> 실제 모델로 실행해 저장한 화면입니다. CPU 91%와 배치 경고가 같아도 배치의 CPU 기여가 5%여서 배치 가설은 반증했습니다. 요청 처리 기여 88%와 요청량 3.2배는 요청량 가설을 교차 지지했습니다. 관측은 교육용 합성 데이터입니다. 오른쪽은 10월 21일 기록으로, 입력 거절 다섯 건의 생성 0토큰과 LLM·MCP 미호출, 테스트 99개 통과를 확인했습니다. 입력 검사 도입 전 실제 가설 평가는 기능 6/6, Judge 포함 종합 5/6이었고 원격 실행 6건과 점수 30개도 재조회했습니다.

**화면에서 짚을 부분**

배치 반증과 요청량 교차 지지의 실제 저장 화면을 짚는다. 오른쪽 검증 표에서 입력 거절과 이전 가설 조사 평가를 구분한다. 전체 조사나 Judge는 재실행하지 않는다.

## 8. 한계와 다음 개선, 배운 점 (35초)

**대응 항목:** 5) 교훈

**발표 멘트**

> 입력 규칙에는 오탐과 미탐이 생길 수 있습니다. 추가 조사는 CPU 세 가설과 합성 관측에 한정되고 최대 네 번의 조회 때문에 미확인 가설도 남을 수 있습니다. 교차 지지는 인과 확정과 구분해야 하며 Judge에도 오류와 편향이 있습니다. 다음에는 실제 모니터링, 사람과 다른 계열 Judge의 교차 평가, 동일 조건의 전체 비용 측정을 진행하겠습니다. 이번 경험으로 자연스러운 설명보다 판단 조건과 근거를 남기는 일이 중요함을 배웠습니다. 결론 보류에도 이유를 보여주는 설계를 이어가겠습니다.

**화면에서 짚을 부분**

한계와 다음 개선을 연결한다. 판단 조건과 근거를 남기는 설계 경험으로 마무리하고 5분에 종료한다.

## 시연과 시간 관리

7번 슬라이드의 실제 저장 화면에서 배치 기여 5% 반증, 요청 처리 기여 88%와 요청량 3.2배 교차 지지를 보여준다. 관측은 교육용 합성 데이터다. 전체 조사와 Judge 재평가는 발표 전에 끝낸 보존 결과를 사용한다.

실시간 시연이 필요하면 7번의 설명 시간 일부를 줄이고 `오늘 날씨 알려줘`를 입력해 거절 이유와 생성 0토큰만 확인한다. 서버가 준비되지 않았다면 [저장된 입력 거절 화면](../artifacts/screenshots/input-rejected-zero-tokens.png)을 사용한다.

## 예상 질문과 답변

**Q. 기존 RAG나 추가 조회와 무엇이 다른가요?**

조회 전에 지지·반증 조건을 기록하고, 경쟁 가설을 구별할 질문을 선택합니다. 최종 답변뿐 아니라 판단이 달라진 이유와 종료 이유도 관측 근거로 남깁니다.

**Q. 실제 AI를 연결했나요? 실제 운영 데이터인가요?**

보존된 실측은 Ollama의 qwen3.5:2b로 계획·작성하고 qwen3:8b로 별도 평가했습니다. 지표·로그·추가 관측은 교육용 합성 데이터입니다. OpenAI 연결도 지원하지만 해당 저장 결과에는 사용하지 않았습니다.

**Q. Multi-Agent는 모든 역할이 각각 LLM인가요?**

지표·로그·런북 역할을 전문 서브그래프로 분리하고 Supervisor가 조정합니다. 전문 조회는 도구와 검색을 담당하며, 실제 LLM은 추가 질문 선택과 보고서 후보 작성에 사용합니다.

**Q. Vector DB는 무엇을 사용했나요?**

매뉴얼 6종에 맞춰 임베딩을 SQLite에 저장하고 NumPy 코사인 유사도로 검색하는 자체 영속 벡터 인덱스를 구현했습니다. Chroma나 FAISS 같은 외부 제품은 사용하지 않았습니다.

**Q. 0토큰이면 전체 비용을 줄였다는 뜻인가요?**

거절한 5건의 생성 토큰이 0이고 LLM·MCP 호출이 없음을 검증한 결과입니다. 전체 요청 대비 절감률과 하드웨어 비용까지 측정한 것은 아닙니다.

**Q. 기능 6/6인데 종합 평가는 왜 5/6인가요?**

릴리스 사례는 기능 조건을 충족했지만 Judge가 근거 점수를 낮게 준 검토 사례입니다. 기능과 의미 평가를 구분하고 원래 실패 점수를 보존했습니다. Judge 역시 오류 가능성이 있습니다.

**Q. 두 근거가 지지하면 원인을 확정할 수 있나요?**

현재 정책에서 교차 지지로 표시할 수 있지만 실제 인과관계 확정은 별도의 운영 검증이 필요합니다. 관측이 상충하거나 부족하면 판단을 보류합니다.

**Q. 왜 추가 조사를 최대 4회로 제한했나요?**

허용한 관측 종류가 네 가지이고 중복을 막아 호출량을 통제하기 위해서입니다. 한도 때문에 미확인 가설이 남을 수 있으며 최소 호출 경로를 수학적으로 보장하지는 않습니다.

**Q. 다음에 가장 먼저 개선할 부분은 무엇인가요?**

실제 모니터링과 프로파일러 연결, 입력 필터의 사람 라벨 평가, 다른 계열 Judge와 사람 평가의 비교입니다. 동일 조건의 호출량·토큰·지연시간도 계측하겠습니다.
